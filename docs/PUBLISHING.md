# GitHub review publishing

Implementation is covered by mocked GitHub calls and PostgreSQL tests. **Live GitHub publishing remains UNVERIFIED** until a real GitHub App is configured and a disposable pull request is tested.

## Policy and user flow

Publishing is off by default. A repository writer can enable publishing in repository settings. Manual mode is the default: open a completed review, choose **Preview feedback**, inspect the feedback, then **Publish this feedback**. The server requires a valid repository write grant and CSRF token. Demo repositories cannot publish.

Automatic mode is a separate explicit repository opt-in. A review completing while both flags are enabled creates a publication record in the same transaction as its results. Enabling automatic mode does not publish historical reviews. Disabling it before dispatch cancels pending automatic requests. Manual requests also recheck the initiating user's current grant before sending; an expired or revoked grant stops the request.

`QUEUE_ENABLED=true` starts the publication dispatcher as well as the analysis workers. Publication records are a PostgreSQL-backed work queue, polled every ten seconds in bounded batches. No private code or findings are sent through RabbitMQ for publishing.

## Validation and formatting

The publisher fetches the current open PR and files, requires the analyzed commit SHA, normalizes the diff again, and checks added-line positions. Only complete, validated added lines receive inline comments (`line`, `side: RIGHT`). Other observations go into the review body. A final metadata check precedes the POST. There remains a small external race if a contributor pushes immediately after that check; pinning `commit_id` keeps feedback attached to the analyzed commit, and GitHub may mark it outdated or reject it.

Feedback is one `COMMENT` review, never an approval or request for changes. Markdown punctuation in untrusted text is encoded; mentions are broken to avoid notifications generated by model/repository content. Suggested fixes are plain text, not executable commands or GitHub suggestion blocks. Text fields are truncated to documented code limits; at most 30 inline comments and a bounded general body are sent. The preview shows escaped Markdown source. Its line placement can change to a general observation after fresh validation.

API contract: [GitHub pull request reviews](https://docs.github.com/en/rest/pulls/reviews?apiVersion=2026-03-10). Required App repository permission: **Pull requests: write**. Installation tokens remain server-side.

## Duplicate prevention and failure handling

`review_publications.job_id` is unique. A database lock serializes requests for a job, and a publication lock permits only one worker to enter `SENDING`. That state commits before the external request. A deterministic UUID marker is included in the review body. Repeating the manual request returns the existing publication.

- `PENDING`: waiting for dispatch.
- `SENDING`: preparation/submission has started.
- `PUBLISHED`: a valid GitHub review ID was received or reconciled.
- `UNKNOWN`: GitHub may have accepted a submission whose response was lost; or a worker stopped after entering `SENDING`. Abandoned sends become unknown after five minutes.
- `FAILED`: preflight failed before a submission was attempted, with a safe failure code.
- `CANCELLED`: policy or authorization prevented dispatch.

There is deliberately **no automatic re-POST** after `SENDING`, even on 401, 429 or 5xx. This favors avoiding duplicate notifications over automatic recovery. In `UNKNOWN`, **Check for existing review** only lists reviews and looks for the publication marker, commit, submitted comment state and bot author. A matching review becomes published. Absence remains unknown because it cannot prove the original POST was not accepted. Reconciliation requires current repository write access and never submits a review.

Failed/cancelled publications are retained and cannot be resubmitted for the same job through the API. Address the reported policy, stale-head or connectivity problem and review a new commit. Do not delete publication rows to force retries: that removes the duplicate guard. Audits record requests, confirmed review IDs, preflight failures and unknown outcomes without private feedback bodies.

## Live verification checklist

Use a disposable repository with an installed App, functioning OAuth, and `QUEUE_ENABLED=true`.

1. Enable repository publishing, leave automatic publishing off, and open a PR containing a changed line that produces a finding in mock/static mode.
2. Wait for a completed review. Preview and publish it as a repository writer. Confirm one GitHub `COMMENT` review on the expected commit and correct changed lines.
3. Repeat the POST from the dashboard session with its CSRF token. Confirm the same publication ID and no second GitHub review.
4. Push a new commit before publishing an older result. Confirm the older result cannot publish. Verify read-only users and users outside the repository cannot publish.
5. Enable automatic publishing, push a fresh commit, and confirm exactly one review is created. Disable the flag again after the test.
6. Test ambiguous-response recovery only in a controlled proxy/test environment: drop the POST response after forwarding it. Confirm `UNKNOWN`, then use read-only reconciliation to recover the existing review ID without another POST.

The deterministic test suite covers timeout/replay behavior without making live requests. No real GitHub comments have been posted during development.
